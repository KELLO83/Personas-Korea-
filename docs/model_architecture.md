# Model and Runtime Architecture

This document describes the current platform architecture and the boundary between runtime services and recommender experiments. Older model-training notes that belonged to recommender experiments should live under `experiments/hobby_recommender_ml/` or `experiments/persona_similarity/`.

## Runtime Layers

```text
frontend/ Next.js UI
        |
        v
src/api/ FastAPI routes and schemas
        |
        +--> src/graph/ Neo4j query and loader helpers
        +--> src/gds/ Neo4j GDS services
        +--> src/rag/ LangChain/LangGraph chat, routing, tracing
        +--> src/embeddings/ KURE embedding wrappers and vector-index helpers
        +--> src/data/ dataset loading and preprocessing
```

## Dependency Baseline

The platform Python stack follows `requirements.txt`:

- FastAPI and Uvicorn for the backend API.
- Neo4j Python driver and Graph Data Science client for graph operations.
- LangChain, LangChain Neo4j, LangChain OpenAI, and LangGraph for RAG/chat orchestration.
- Sentence Transformers and PyTorch for local embedding workflows.
- pandas, Polars, PyArrow, OpenPyXL, and Hugging Face datasets for data processing.
- psycopg for PostgreSQL/pgvector loading utilities.
- LangSmith and Phoenix/OpenTelemetry packages as opt-in observability integrations.

The frontend stack follows `frontend/package.json`:

- Next.js 16.
- React 19.
- TypeScript 5.
- D3/d3-force and ECharts for visualization.

## Graph Model

The runtime graph is centered on `Person` nodes and connected attribute/entity nodes such as region, occupation, hobby, skill, education, and community-related attributes.

Primary relationship families include:

- Residence and location relationships.
- Occupation and education relationships.
- Hobby and skill relationships.
- Similarity relationships generated by GDS workflows.
- Community and centrality properties written by batch jobs.

## Embedding and RAG Model

The current platform uses KURE-style Korean text embeddings through `src/embeddings/` and vector/RAG helpers under `src/rag/`.

RAG flow:

1. The API receives a chat or insight request.
2. LangGraph/LangChain routing chooses a graph/stat/search/vector path.
3. Neo4j or vector-index evidence is fetched.
4. The response is shaped through schemas in `src/api/schemas.py`.
5. Optional tracing records latency, status, and metadata without secrets.

## Recommender Boundary

The root platform does not own recommender training decisions.

| Track | Location | Runtime Contract |
|---|---|---|
| Hobby recommendation | `experiments/hobby_recommender_ml/` | Root API may consume promoted artifacts through an adapter. |
| Similar-persona recommendation | `experiments/persona_similarity/` | Root API may consume promoted artifacts through an adapter. |

Until a promoted artifact is documented in the owning experiment folder, the root API should keep graph/rule fallback behavior.

## Operational Scripts

Current script routing:

- `ops/data/`: dataset download and preview.
- `ops/graph/`: Neo4j graph build, GDS build, and display-name backfill.
- `ops/vector/`: embedding build and pgvector load.
- `ops/dev/`: local environment checks.

Long-running graph, GDS, and embedding work must run through ops entrypoints or jobs, not FastAPI request handlers.
